# Meetings API

Навчальний REST API для керування зустрічами, учасниками та файлами. Фінальний проєкт курсу ASP.NET в Академії ITStep.

Застосунок демонструє роботу з ASP.NET Core, Entity Framework Core, SQL Server, Identity, JWT, MediatR, FluentValidation, AutoMapper та Serilog. Взаємодія і демонстрація виконуються через Swagger UI; окремого frontend у цьому проєкті немає.

## Можливості

- Реєстрація користувачів зі створенням профілю учасника, вхід та отримання JWT.
- Ролі `User` і `Admin`, обмеження доступу до операцій.
- Створення, перегляд, повне та часткове оновлення зустрічей, одиночне й масове видалення.
- Призначення учасників зустрічі та перегляд зустрічей певного учасника.
- Перевірка зайнятості кімнати з умовною тривалістю зустрічі три години.
- Перегляд та редагування профілів учасників, завантаження аватарів.
- Пошук, фільтрація, сортування та пагінація списків.
- Публічні вкладення зустрічей і приватний обмін файлами між учасниками.
- Валідація запитів, обробка винятків, обмеження частоти запитів.
- Логування в консоль, файли та SQL Server; Correlation ID для запитів.
- Кероване конфігурацією початкове заповнення БД тестовими даними.

## Технології та архітектура

| Компонент | Призначення |
| --- | --- |
| .NET 10 / ASP.NET Core | Web API на контролерах |
| SQL Server / EF Core 10 | Зберігання даних, зв'язки сутностей та міграції |
| ASP.NET Core Identity / JWT Bearer | Облікові записи, паролі, ролі й автентифікація |
| MediatR | Передавання команд і запитів обробникам |
| FluentValidation | Правила перевірки вхідних даних |
| AutoMapper | Перетворення сутностей у DTO, проєкція списків через `ProjectTo` |
| Serilog | Структуровані журнали подій |
| Swagger / Asp.Versioning | Документація API, інтерактивні запити, версіонування |
| Bogus | Генерація демонстраційних даних |

Точні версії пакетів зазначені в [HW_06.csproj](HW_06/HW_06.csproj).

Проєкт організований за функціональними модулями. Команди змінюють дані, запити повертають дані; для обох використовується одна БД. Це поділ у стилі CQRS, а не окремі сховища читання та запису.

Контролер передає запит через `ISender`. `ValidationBehavior` запускає валідатори, після чого handler виконує операцію через `DataContext` та повертає результат. DTO відокремлюють зовнішній контракт API від моделей БД.

Шляхи нижче наведені відносно папки `HW_06`:

| Папка / файл | Вміст |
| --- | --- |

| `Helpers` | Пошук, сортування, пагінація, початкове заповнення |
| `Middleware` | Обробка винятків, Correlation ID, режим обслуговування |
| `Services` | Допоміжні сервіси, зокрема токени та файлове сховище |

Зустрічі та учасники пов'язані через `MeetingParticipant` (many-to-many). Кімната може мати багато зустрічей. Профіль учасника пов'язаний з `ApplicationUser`; організатор зустрічі визначається за поточним користувачем.

## Запуск проєкту

### Вимоги

- .NET 10 SDK.
- Запущений SQL Server і доступ до створення / оновлення навчальної БД.
- Git та інструмент `dotnet-ef` версії, сумісної з EF Core у проєкті.
- Rider або Visual Studio — за бажанням; запуск можливий із термінала.

Нижче наведено приклад для Windows і PowerShell з Windows Authentication у SQL Server. Для іншого екземпляра SQL Server потрібно змінити `Server` у рядку підключення.

### 1. Отримати код

```powershell
git clone https://github.com/AStrelko/HW_ASP.NET.git
cd HW_ASP.NET/Meetings_Final_Project/HW_06
dotnet restore
```

Усі наступні команди виконуються з папки, де розташований `HW_06.csproj`. Якщо репозиторій уже є, відкрийте цю папку у своїй копії; повторне клонування не потрібне.

### 2. Налаштувати локальне середовище

Створіть `appsettings.Development.json` поруч із `appsettings.json`. Якщо файл уже існує, об'єднайте налаштування, не створюючи повторних JSON-ключів.

Приклад без реальних секретів:

```json
{
  "ConnectionStrings": {
    "DefaultConnection": "Server=localhost;Database=MeetingsDemoDB;Integrated Security=True;TrustServerCertificate=True;Encrypt=False;"
  },
  "Jwt": {
    "Issuer": "http://localhost:5165",
    "Audience": "meeting-api-client",
    "Key": "",
    "AccessTokenMinutes": 15
  },
  "Seed": {
    "Enabled": true
  },
  "Maintenance": {
    "Enabled": false
  },
  "FileStorage": {
    "MaxAvatarSizeMb": 5,
    "MaxPublicDocumentSizeMb": 10,
    "MaxPrivateDocumentSizeMb": 10
  },
  "Serilog": {
    "MinimumLevel": {
      "Default": "Information",
      "Override": {
        "Microsoft": "Warning",
        "Microsoft.EntityFrameworkCore": "Warning"
      }
    }
  }
}
```

`MeetingsDemoDB` — окрема навчальна база, щоб не змінювати вже наявну `HW06DB`. За потреби використовуйте власну назву. Параметри довіри сертифікату в цьому прикладі призначені для локальної демонстрації, а не production.

Замість публікації JWT-ключа задайте його через змінну середовища. Наступні команди генерують випадковий ключ для поточного сеансу PowerShell, не виводячи його в консоль:

```powershell
$jwtKeyBytes = New-Object byte[] 32
$jwtKeyGenerator = [System.Security.Cryptography.RandomNumberGenerator]::Create()
$jwtKeyGenerator.GetBytes($jwtKeyBytes)
$jwtKeyGenerator.Dispose()
$env:Jwt__Key = [Convert]::ToBase64String($jwtKeyBytes)
$env:ASPNETCORE_ENVIRONMENT = "Development"
```

Запускайте застосунок із цього самого термінала. Після його закриття змінну потрібно задати знову. Новий ключ робить раніше видані токени недійсними — виконайте повторний вхід. Для запуску через IDE задайте ключ у локальних налаштуваннях середовища запуску або в ігнорованому файлі Development.

Подвійне підкреслення у `Jwt__Key` відповідає вкладеному ключу `Jwt:Key`. Змінні середовища мають пріоритет над JSON-конфігурацією. [Документація конфігурації ASP.NET Core](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/configuration/?view=aspnetcore-10.0).

Не комітьте локальні секрети, журнали та завантажені користувачами файли. Правило `.gitignore` не прибирає файл, який уже відстежується Git, і не очищує минулу історію.

### 3. Застосувати міграції

Якщо інструмент ще не встановлений:

```powershell
dotnet tool install --global dotnet-ef --version 10.0.11
```

Якщо встановлений інший варіант, перевірте `dotnet ef --version` і за потреби оновіть його до версії пакетів проєкту. Після зміни пакетів звіряйте версію з `HW_06.csproj`.

```powershell
dotnet ef database update
```

Міграції вже включені в проєкт. Для звичайного запуску створювати нову міграцію або видаляти наявну БД не потрібно. [Довідка EF Core CLI](https://learn.microsoft.com/en-us/ef/core/cli/dotnet).

### 4. Запустити API

```powershell
dotnet dev-certs https --trust
dotnet run --launch-profile https
```

Відкрийте [Swagger UI](https://localhost:7036/swagger). Профіль `https` використовує HTTPS-порт `7036` і HTTP-порт `5165`; остаточну адресу дивіться у повідомленні `Now listening on`.

Swagger підключається в середовищі `Development`. Відсутність Swagger у production не означає, що API не працює. Параметри профілів містяться в [launchSettings.json](HW_06/Properties/launchSettings.json).

## Тестові дані та перший вхід

`Seed:Enabled` перевіряється в `Program.cs`:

| Умова | Результат |
| --- | --- |
| `false` або параметр відсутній | Початкове заповнення не викликається |
| `true`, користувачів, учасників, кімнат і зустрічей немає | Генеруються тестові дані |
| `true`, хоча б одна з цих груп містить дані | Заповнення пропускається |

Наявність лише ролей не заважає заповненню. Частково заповнена база автоматично не доповнюється. Прапорець не видаляє дані та не замінює міграції.

Генератор створює ролі `Admin` і `User`, 10 кімнат, до 30 користувачів із профілями учасників, 20 зустрічей та зв'язки між ними. Перший успішно створений профіль отримує роль `Admin`, інші — `User`. Імена, email і зустрічі генеруються випадково.

### Як знайти адміністратора

У своїй навчальній БД виконайте через Rider Database або SQL Server Management Studio:

```sql
SELECT u.Email, r.Name AS RoleName
FROM AspNetUsers AS u
INNER JOIN AspNetUserRoles AS ur ON ur.UserId = u.Id
INNER JOIN AspNetRoles AS r ON r.Id = ur.RoleId
WHERE r.Name = N'Admin';
```

Пароль згенерованих демонстраційних користувачів: `Test123` (якщо його не було змінено). Це навмисно відомий навчальний пароль, а не безпечні облікові дані для публічного сервера. Не публікуйте розгорнутий застосунок із такими акаунтами. Вимкнення Seed не видаляє їх із наявної БД.

### Вхід у Swagger

1. Виконайте `POST /api/auth/login` з email знайденого адміністратора та демонстраційним паролем.
2. Скопіюйте значення access token з відповіді, без JSON-лапок.
3. Натисніть **Authorize** та вставте лише токен: Swagger додає префікс `Bearer` автоматично.
4. Для перевірки звичайного користувача зареєструйте новий акаунт через `POST /api/auth/register`. Він отримує роль `User` і профіль учасника.

Для інших HTTP-клієнтів використовуйте заголовок `Authorization: Bearer <token>`. Після зміни ролі потрібно отримати новий токен; уже виданий токен містить попередню роль.

## Пошук, фільтрація та пагінація

| Параметр | Зустрічі | Учасники |
| --- | --- | --- |
| `Page` | Номер сторінки від 1; типово 1 | Аналогічно |
| `PageSize` | Від 1 до 100; типово 10 | Аналогічно |
| `Search` | Назва або опис | Ім'я, прізвище або email |
| `SortBy` | `id`, `title`, `date`, `room`, `participants` | `id`, `firstname`, `lastname`, `email`, `position` |
| `Descending` | Зворотний порядок; типово `false` | Аналогічно |
| `StartTime`, `EndTime` | Межі дати початку зустрічі включно | Не застосовуються |
| `RoomNumber` | Номер кімнати, не її ID | Не застосовується |

У перевіреній версії сортування зустрічей без `SortBy` виконується за датою, учасників — за ID. Для явного сортування за ідентифікатором передавайте `SortBy=id`. Додаткове сортування за ID забезпечує визначений порядок записів з однаковим основним значенням.

Приклади відносних URL:

```text
/api/v2/meetings?Page=1&PageSize=10&SortBy=id
/api/v2/meetings?RoomNumber=103&SortBy=date&Descending=true
/api/v2/participants?Search=Ivan&Page=1&PageSize=10&SortBy=lastname
```

Відповідь списку має формат `PagedResult<T>`: елементи, загальна кількість, номер і розмір сторінки та допоміжні дані пагінації. Порожній результат пошуку є успішною відповіддю, а не помилкою.

## Правила зустрічей

- Клієнт передає номер кімнати (`RoomNumber`), а не її внутрішній ID. Для створення / повного оновлення `null` означає зустріч без кімнати.
- Зайнятість перевіряється для інтервалу від початку зустрічі до початку плюс три години. Сусідні інтервали, що лише торкаються межами, не конфліктують.
- Під час оновлення поточна зустріч виключається з перевірки конфліктів. Для PATCH враховуються передані та збережені значення дати й кімнати.
- При створенні та відповідних змінах дати субота й неділя відхиляються валідатором. Це помилка валідації, а не інформаційне попередження.
- Перевіряються існування кімнати, зазначених учасників та коректність полів DTO.
- Повне оновлення замінює список учасників. PATCH змінює лише підтримувані передані поля; `null` для кімнати в PATCH не видаляє її призначення.

Час завершення окремо не зберігається. Повноцінне керування часовими поясами не реалізоване; для локальної демонстрації використовуйте узгоджений локальний час сервера. Seed записує дані без проходження командних валідаторів, тому згенеровані зустрічі можуть випадати на вихідні або мати перетини.

| Публічний документ | PDF, DOCX, TXT | 10 МіБ |
| Приватний документ | PDF, DOCX, TXT | 10 МіБ |

Межі задаються через `FileStorage`. Додаткові HTTP-обмеження можуть відхилити запит раніше за файлову валідацію; збільшення опцій саме по собі не змінює атрибути обмежень на контролерах.

Завантаження виконується як `multipart/form-data`. Перевіряються розмір, ім'я, розширення, MIME-тип та вміст відповідно до реалізованого валідатора. Це не антивірусна перевірка.

Оригінальне ім'я зберігається в метаданих; для документів ім'я на диску генерується через GUID. Файли розміщуються відносно кореня застосунку:

- `uploads/PublicFile/Avatars` — аватари;
- `uploads/PublicFile/Documents` — документи зустрічей;
- `uploads/PrivateFile/Participants` — приватні документи.

Каталог `PublicFile` підключений як статичні файли за `/uploads`: прямі посилання на наявні публічні файли не вимагають JWT, хоча контролерні маршрути скачування захищені. Приватний каталог як статичний не публікується. Не розміщуйте конфіденційні документи у публічному сховищі.

Після успішного збереження запису в БД помилка формування DTO не спричиняє видалення документа. Водночас БД і файлове сховище не об'єднані в одну атомарну транзакцію. Для резервної копії потрібні і база, і файли: копіювання лише БД не відновить завантаження.

## Безпека, помилки та логування

### Автентифікація та обмеження запитів

JWT перевіряється за підписом, видавцем, аудиторією і строком дії. Паролі обробляє ASP.NET Core Identity. Реалізовані рольова авторизація, HTTPS redirection і HSTS поза Development.

Іменована CORS-політика `Frontend` читає `Cors:AllowedOrigins`. Типові адреси — `http://localhost:3000` та `http://localhost:5173`. CORS стосується браузерних запитів і не замінює автентифікацію.

| Обмеження за IP | Кількість | Фіксоване вікно |
| --- | --- | --- |
| Глобальне для запитів, які проходять rate limiter | 100 | 1 хвилина |
| Login | 5 | 5 хвилин |
| Register | 5 | 10 хвилин |

Черга вимкнена. Ліміт рахує запити незалежно від правильності пароля. При перевищенні повертається `429` і, коли доступна відповідна інформація, заголовок `Retry-After`. Ліміти зберігаються в пам'яті процесу; це не розподілений захист. Облік невдалих спроб входу Identity є окремим механізмом.

### Відповіді про помилки

| Код | Значення |
| --- | --- |
| 400 | Некоректні дані / помилка валідації |
| 401 | Немає дійсного токена або невдалий вхід |
| 403 | Недостатньо прав |
| 404 | Ресурс не знайдено |
| 413 | Перевищено допустимий розмір запиту |
| 429 | Перевищено частоту запитів |
| 500 | Неочікувана серверна помилка |
| 503 | Увімкнено режим обслуговування |

Глобальний middleware обробляє винятки; відповіді JWT 401/403 та помилки контролера зустрічей оформлені через `ProblemDetails`. Для помилок FluentValidation використовується `ValidationProblemDetails` із полем `errors`. Частина інших контролерів ще повертає власні об'єкти помилок — повна уніфікація не завершена.

У підтримуваних відповідях `traceId` допомагає діагностиці. Окремий middleware додає заголовок `X-Correlation-ID` та властивість `CorrelationId` у журнали. Це різні ідентифікатори, їхні значення не зобов'язані збігатися.

### Журнали

- Console — події в терміналі.
- File — щоденна ротація на основі шляху `logs/myapp.log`, зберігання до 14 файлів.
- SQL Server — таблиця `Logs`, яка створюється sink за наявності необхідних прав.
- Типовий рівень базової конфігурації — `Warning`; у наведеному Development-файлі — `Information`. Категорії Microsoft та EF Core обмежені рівнем `Warning`.

Перегляд останніх SQL-записів у налаштованій БД:

```sql
SELECT TOP (50) *
FROM dbo.Logs
ORDER BY Id DESC;
```

SQL-журнал може заповнюватися із затримкою. Якщо таблиця порожня, перевірте рівень логування, підключення та права SQL-користувача. Секрети й вміст приватних файлів не слід додавати до логів.

`Maintenance:Enabled = true` вмикає режим технічного обслуговування з відповіддю `503`. Для демонстрації залишайте `false`.

## Перевірка через Swagger

Ручний сценарій перевірки; він не є автоматизованим тестовим набором:

1. Запустити застосунок і відкрити Swagger.
2. Увійти адміністратором; перевірити отримання JWT та кнопку Authorize.
3. Отримати списки зустрічей і учасників, змінити пошук, сортування та сторінку.
4. Створити зустріч на майбутній робочий день з наявними учасниками й вільною кімнатою.
5. Спробувати створити зустріч із перетином часу в тій самій кімнаті; очікувати відхилення валідацією.
6. Перевірити PUT / PATCH та детальний перегляд створеної зустрічі.
7. Завантажити й скачати публічний документ.
8. Надіслати приватний файл іншому учаснику; увійти отримувачем і скачати його. Перевірити відмову сторонньому учаснику.
9. Без токена запросити захищений список зустрічей — очікувати `401`.
10. З роллю User викликати адміністративне видалення з неіснуючим додатним ID — очікувати `403`, не видаляючи реальні дані.
11. З токеном запросити неіснуючу зустріч — очікувати `404`; передати `PageSize=500` — очікувати `400`.
12. Перевірити ліміт входу швидкими запитами — очікувати `429`. Врахувати час очікування перед подальшою демонстрацією login.
13. Переглянути консоль, файл журналу та SQL-таблицю `Logs`.

Перед демонстрацією бажано пройти інструкцію на окремій навчальній БД. Ручна перевірка основних операцій не гарантує відсутність усіх помилок або готовність до production.

## Межі навчальної реалізації

- Моделі та структура адаптовані до вже створеного навчального проєкту; це не буквальне відтворення всього початкового ТЗ.
- Кімнати створюються початковим заповненням. Окремого CRUD-контролера кімнат немає.
- Зовнішній API державних свят, його кешування та політики стійкості не реалізовані.
- Endpoint `/health` не реалізований.
- Правила доступу відповідають таблицям вище: автор зустрічі не отримує автоматичного права її редагування замість Admin.
- Перевірка бронювання у валідаторі не гарантує захисту від двох одночасних конкурентних запитів на ту саму кімнату.
- Seed генерує випадкові номери кімнат без гарантії унікальності та не перевіряє зустрічі командними валідаторами. Це демонстраційні, а не виробничі дані.
- Формат помилок не уніфікований для абсолютно всіх маршрутів.
- Перед публічним розгортанням потрібні окрема перевірка безпеки, залежностей, облікових записів, анонімного доступу до списку учасників, файлового сховища та налаштувань reverse proxy.

Відеодемонстрацію та окреме покрокове керівництво зі створення проєкту буде додано пізніше.
